# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local Windows desktop app (Electron + React + TypeScript) for creating network topology diagrams. The core feature: the user types a free-text description of an infrastructure (e.g. "2 servidores, 1 NAS, 1 pfSense, 4 Ubiquiti, 4 switches, VPN, VLANs") and a locally-running LLM (via Ollama, not a cloud API — see "AI backend" below) converts it into a structured diagram, which streams onto an editable React Flow canvas in real time and can then be freely edited by hand (drag nodes, add/remove devices and connections, edit properties).

## Commands

- `npm run dev` — start the app in dev mode (electron-vite dev server + Electron window, with renderer HMR). **Main/preload process changes require a full restart** (close the window, re-run `npm run dev`) — only renderer (React/CSS) changes hot-reload.
- `npm run build` — production build of main/preload/renderer into `out/`.
- `npm run build:win` — production build + package a Windows installer via electron-builder into `release/` (config in `electron-builder.yml`).
- `npm run typecheck` — type-checks main/preload (`tsconfig.node.json`) and renderer (`tsconfig.web.json`) separately; run this after any change, it's the fastest correctness signal.
- `npm run test` — runs the Vitest suite (`vitest.config.ts`, Node environment, no DOM). Covers pure `lib/` modules and `diagramStore.ts`'s actions directly via `useDiagramStore.getState()` (zustand stores work fine outside React). Deliberately does **not** cover React components — that would need jsdom/testing-library and isn't set up. Tests are colocated as `*.test.ts` next to the module they cover.

## AI backend: local Ollama, not a cloud API

This was originally built against the Anthropic API, then migrated to a **local Ollama** instance to avoid per-use API costs. Ollama must be installed and running on the user's machine (`http://localhost:11434` by default, configurable in the app's Settings modal) with a model pulled (default `qwen2.5:7b`; lighter option `llama3.2:3b` for weaker GPUs). There is no API key anywhere in this app.

Structured output is obtained via Ollama's `format` parameter (JSON Schema-constrained decoding), not tool-calling — this works consistently across open models. The schema passed as `format` is generated at runtime from the zod schema in `src/shared/diagramSchema.ts` via `z.toJSONSchema()` (zod v4's built-in JSON Schema export — do not add the third-party `zod-to-json-schema` package, it predates/conflicts with zod v4's internal types).

Generation is **streamed** (`src/main/llm/client.ts`): the main process reads Ollama's NDJSON stream, accumulates `message.content` deltas, and throttles (~150ms) pushes of the accumulated raw text to the renderer over the `diagram:generateProgress` IPC channel (see "IPC" below), so the UI can render devices/connections/VLANs as they're generated rather than only at the end. If the final response fails schema validation, whatever was already streamed onto the canvas is left in place (not cleared) — this is intentional, so the user can see how far generation got.

## Architecture

Standard electron-vite three-target layout, with a `src/shared/` folder imported by both main and renderer (path-aliased as `@shared/*`; renderer also has `@renderer/*`):

- `src/main/` — Node/Electron process. `index.ts` boots the window; `ipcHandlers.ts` wires every `ipcMain.handle` to its implementation. `llm/` holds the Ollama client, the JSON-schema-from-zod conversion (`diagramJsonSchema.ts`), and the system prompt (`prompt.ts`, which instructs the model on device-type mapping, VPN/VLAN inference conventions, and the `refId` scheme below). `settings/appSettings.ts` persists Ollama host/model choice as plain JSON in `app.getPath('userData')`. `fileIO/` handles native save/open dialogs for diagram JSON and PNG export.
- `src/preload/index.ts` — the only bridge between renderer and main, via `contextBridge.exposeInMainWorld('diagramAPI', ...)`. The typed shape of this API lives in `src/shared/ipc.ts` (`DiagramAPI` interface) — extend that interface, the `IPC` channel-name map, preload, and the `ipcMain.handle` registration together; they must stay in lockstep.
- `src/renderer/` — the React app.
  - `state/diagramStore.ts` — single zustand store holding the canvas's `nodes`/`edges`/`vlans`. This is the one place where **LLM-generated data, streaming-partial data, and manually-edited data all converge into the same shape** (`Node<DeviceNodeData>` / `Edge<ConnectionEdgeData>`) — there is no separate "AI diagram" representation. Key actions: `beginGeneration()` (clears canvas, resets the streaming refId→uuid map), `applyPartialGeneratedDiagram()` (called on every streamed chunk; places new nodes on an incremental grid, preserves already-placed positions), `applyGeneratedDiagram()` (called once on the final validated result; re-lays out everything via dagre), `autoArrange()` (re-runs the dagre layout on demand, exposed as a toolbar button), plus the usual manual CRUD actions.
  - `lib/layout.ts` — dagre-based hierarchical (top-down) auto-layout; spacing scales up for larger diagrams (40+/20+ node thresholds) since hub devices (core switches, firewalls) accumulate many redundant edges and need more room.
  - `lib/partialDiagramParser.ts` — wraps the `partial-json` package to best-effort-parse the (possibly truncated, mid-stream) JSON text into complete devices/connections/VLANs only; an object still missing required fields is simply excluded until a later chunk completes it. This is what lets `applyPartialGeneratedDiagram` render incrementally.
  - `components/nodes/DeviceNode.tsx` / `components/edges/ConnectionEdge.tsx` — custom React Flow node/edge renderers. Device visual identity (icon, gradient, label) is centralized in `lib/deviceTypeConfig.ts`; VLAN/VPN edge coloring in `lib/vlanColors.ts` (VPN edges get an animated dashed stroke; VLAN edges are colored deterministically by `vlanId`).

  ### Every connection side must register as *both* source and target (`DualHandle`)

  `connectionMode="loose"` (set on `<ReactFlow>` in `DiagramCanvas.tsx`) lets a user start or end a drag on any of a device's 4 sides. It's tempting to give each side a single fixed `type` (e.g. top/left = `"target"`, bottom/right = `"source"`) since that's what a plain top-down diagram needs — **this silently breaks any connection between two same-typed sides** (e.g. left-to-left, or top-to-top): loose mode's own validation allows it, the drag visually completes, but React Flow's edge renderer looks up the resolved `sourceHandle` id in the source node's *source*-type handle registry and the resolved `targetHandle` id in the target node's *target*-type registry — one of those lookups fails for a same-typed pair, so the edge is silently dropped (logs `Couldn't create edge for source/target handle id` to the console, never appears, `commitHistory` still ran so it even eats an undo step). This was a real regression, root-caused by scripting the exact drag with Playwright against the renderer served standalone (`vite` on `src/renderer` directly, bypassing Electron, with `window.diagramAPI` stubbed) rather than guessing from a screenshot.

  Fixed with `DualHandle` (defined at the top of `DeviceNode.tsx`): each of the 4 positions renders **two** stacked `<Handle>`s, one `type="source"` and one `type="target"`, sharing the same `id` and `position`. Whichever DOM element ends up capturing a given interaction, both types are now pre-registered at every position on every node, so the render-time lookup always succeeds regardless of which two sides get connected. Do not revert this to a single Handle per side without re-verifying same-type pairs (left-left, top-top, right-right, bottom-bottom) — the failure is invisible in code review and only shows up as "this specific pair of sides doesn't connect" during manual testing.
  - `components/DevicePalette.tsx` / `lib/devicePresets.ts` — the manual "add device" palette. The LLM/data model only knows the 8 base `DeviceType`s, but the palette offers ~21 specific presets (router, modem, VM, database, storage, notebook, printer, CCTV camera, IP phone, UPS, load balancer, branch/site, etc.) with a search box. Each preset maps to one base `DeviceType` (for color/gradient/LLM-compatibility) but also carries its own `iconKey` (from the registry in `lib/deviceIcons.ts`) that gets written onto the placed node as `DeviceNodeData.icon` — this is what makes e.g. "Banco de Dados" render with a database icon on the canvas instead of falling back to the generic server icon for its underlying type. `DeviceNode.tsx` resolves the icon as `DEVICE_ICONS[data.icon] ?? deviceTypeConfig[data.type].icon`.
  - `state/tabsStore.ts` / `components/TabBar.tsx` — multiple diagrams open at once as tabs. Only the *inactive* tabs' `Diagram` snapshots live in `tabsStore`; the active tab's live content stays in `diagramStore` as always (storing a copy of the active tab would go stale on every edit). Switching tabs round-trips through `diagramStore.toDiagram()` (snapshot out) / `loadDiagram()` (load in). "Novo diagrama" and "Abrir" in the toolbar open into a new tab instead of discarding the current one.
  - Undo/redo lives inside `diagramStore.ts` itself (`historyPast`/`historyFuture` module-level arrays of `{nodes,edges,vlans}` snapshots, plus `canUndo`/`canRedo` reactive flags). `commitHistory(get, set, force)` is called before every mutation; rapid repeats (typing in a field, dragging a node) within `HISTORY_GROUP_MS` collapse into one undo step unless `force` is passed (discrete actions: add/remove/duplicate/paste-generation/autoArrange). Bound to Ctrl+Z/Ctrl+Shift+Z/Ctrl+Y in `DiagramCanvas.tsx`'s keydown handler (skipped while focus is inside a text input). `loadDiagram()`/`newDiagram()` reset history entirely — undo does not cross a tab switch or file load.
  - `lib/networkAudit.ts` / `components/AuditModal.tsx` — "Analisar diagrama" in the toolbar (`Stethoscope` icon). Deliberately **rule-based, not AI**: `auditDiagram(diagram)` is a pure function scanning graph structure only (isolated devices, duplicate IPs, infra devices with no IP/VLAN, VLANs with no gateway IP or that nobody references, VMs wired directly to a switch/firewall instead of their host, overloaded switches with a single non-redundant uplink, firewalls with no internet/cloud link anywhere in the diagram). It's instant, free, and works with Ollama off. Rules that would need the original free-text prompt to judge intent (e.g. "should this have a VPN?") are deliberately left out — that context doesn't survive past generation, so a rule like that would just be a constant false-positive machine. `AuditModal` recomputes via `useMemo` keyed on the reactive `nodes`/`edges`/`vlans` slices (not on `toDiagram()`, which isn't itself reactive).
  - `lib/duplicateDetection.ts` — after a generation finishes, `PromptPanel.tsx` diffs the LLM's returned devices against the pre-generation `existingDevices` list (same heuristic used to build that context: normalized-label + type match) and, if it finds likely re-creations instead of references, shows `DuplicateWarningModal` before committing. "Desfazer geração" there is just `diagramStore.undo()` — it works because `beginGeneration()` forces a history commit of the pre-generation state.
  - `state/uiPreferencesStore.ts` — theme (system/light/dark) and canvas grid (variant + gap), persisted to `localStorage`, edited from Settings. Theme is applied by `App.tsx` setting `document.documentElement.dataset.theme`, and `index.css` has `:root[data-theme="dark"|"light"]` blocks that out-specificity (not out-order) the `prefers-color-scheme` media query so an explicit choice always wins.
  - `lib/inventoryCsv.ts` — builds a semicolon-separated (pt-BR Excel-friendly) CSV of every device + VLAN, exported via the same generic `file:exportFile` IPC channel as PNG/SVG/PDF (as a plain non-base64 `data:text/csv,...` URL — `exportFile.ts` in main already handles that case).
  - Prompt history (`PromptPanel.tsx`) is renderer-only `localStorage`, not IPC/main state — it's just remembered strings, not diagram data.
  - `lib/diagramTemplates.ts` / `components/TemplatesModal.tsx` — hand-authored starter `Diagram`s (small office, matriz+filial VPN, Hyper-V host+VMs+backup), not LLM-generated — picking one loads it (into a new tab if the current one has content) and immediately calls `autoArrange()` since templates only carry placeholder `{x:0,y:0}` positions.

### Group nodes: real parent/child nesting

Group frames (`DeviceType === 'group'`, added via `addGroupNode`) are the one place this app uses React Flow's native `parentId` nesting instead of the flat "everything is an independent node" model everything else uses. `DeviceNodeData.groupId` is the persisted/serializable form; `deviceNodeFromData` derives the top-level `Node.parentId` from it on every construction path, so it's the single normalization point — never set `parentId` by hand elsewhere. `Node.position` becomes relative-to-parent the moment `parentId` is set (a React Flow contract, not this app's choice), which has two consequences to keep in mind when touching this code:

- `reparentIfDropped(id)` (called from `DiagramCanvas`'s `onNodeDragStop`) does all its containment math in *absolute* coordinates — it resolves relative→absolute using the current parent's position before testing which group frame (if any) the node's center now falls inside, then converts back to relative for whichever group it lands in (or leaves absolute if none). Reparenting into a different group happens in one step; there's no intermediate "unparented" state mid-drag.
- `layoutDiagram()` excludes any node with `data.groupId` set (alongside `image`/`group` nodes themselves) — dagre computes absolute-space positions, which would be wrong to write into a relative `position`.
- `removeDevice()` on a group cascades: children get released back to absolute positioning (converted using the group's last known position) rather than left with a `groupId` pointing at a node that no longer exists.

Deliberately **not** implemented: resizing a group doesn't re-check which children still fall inside it, and there's no "drag the group, watch children ride along" special-casing needed in this codebase — that part is entirely native React Flow behavior once `parentId` is set.

### A position-sync gotcha worth knowing about

`DeviceNodeData.position` (used by `toDiagram()`/save/export) and the React Flow `Node.position` (used for rendering/dragging) are two separate fields that only `onNodesChange` keeps in sync (by re-deriving `data.position` from `node.position` after every `applyNodeChanges` call). Any code that constructs or mutates a node's position *outside* that path — new store actions, tests, anything — must update both, or a dragged node will silently revert to its old spot on the next save/tab-switch/export. This was a real bug found while building group nesting (fixed in the same change); `layout.test.ts` asserts the two stay equal as a regression guard.

### The `refId` indirection

The LLM never sees or generates real node ids. Its schema (`llmDiagramSchema` in `src/shared/diagramSchema.ts`) uses a `refId: string` per device that's only meaningful *within a single generation response* (e.g. `"sw-1"`), and connections reference devices via `sourceRefId`/`targetRefId`. The store maps these to stable `uuid()`s (`streamRefMap` in `diagramStore.ts`, module-level state scoped to one generation). This exists because streaming needs a device to keep the same canvas node identity across chunks as more of its fields arrive — a plain array-index key would break the moment the model reorders or the array is still growing.

### Data model boundary

`src/shared/types.ts` (`Diagram`, `DeviceNodeData`, `ConnectionEdgeData`, `Vlan`) is the one format used for the LLM's final (validated) output, manual edits, and the save/load JSON file format alike. `DeviceNodeData`/`ConnectionEdgeData` carry a `[key: string]: unknown` index signature *only* so they satisfy React Flow's `Node<T extends Record<string, unknown>>` generic constraint — not because arbitrary extra fields are expected. `DeviceNodeData.icon` is the one field that's manual-only (never set by the LLM) — see the palette-preset note above.

`src/shared/diagramSchema.ts` has two zod schemas that must not be confused: `diagramSchema` (strict, matches `Diagram` exactly — used for save/load file validation) and `llmDiagramSchema` (the `refId`-based shape described above — used to validate/type the LLM's output before it's translated into real ids by the store).
